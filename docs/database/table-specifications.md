# Table specifications

## Reading this specification

Every table in this document is **proposed** unless it is explicitly marked as an existing concept. It specifies logical columns and invariants, not executable migration SQL. To keep the design reviewable, common columns are defined once below and then inherited by each table. Names in backticks are physical target names. `PK` is the primary key; every table uses a UUID `id` unless stated otherwise. All tenant-owned records have `workspace_id uuid NOT NULL`; all client-owned records also have `client_id uuid NOT NULL`. The common tenant FK is `workspace_id → workspaces.id ON UPDATE RESTRICT ON DELETE RESTRICT`. Client tables additionally have a composite FK `(workspace_id, client_id) → clients(workspace_id,id)` with the same actions. Timestamps are `timestamptz NOT NULL DEFAULT now()` unless called immutable event time (`occurred_at`).

`created_at` is not included in every row description below but is present on every mutable entity. `updated_at timestamptz NOT NULL DEFAULT now()` is present on mutable rows and maintained server-side. Append-only events/snapshots have `created_at` or `occurred_at`, no `updated_at`, and no delete grant. Unique/composite keys described below are required to support tenant-safe foreign keys. UUID FKs use `ON UPDATE RESTRICT`; delete is `RESTRICT` by default, with limited cascade called out explicitly. Add indexes on FK columns where not covered by a leading composite index.

## Excluded existing invoice subsystem

Current schema/migrations include invoice number sequences, invoices, invoice items, invoice payments, invoice revisions, invoice activity events and agency billing profiles. These are verified existing objects, but the requested MVP explicitly excludes invoice management. Keep them as a legacy operational domain pending a decision; do not treat invoice totals/payments as posted GL journals, auto-post them, or drop them as part of this design. Any future bridge needs a source reference, reconciliation rules and an approved migration plan.

## Global constraint and deletion policy

For every same-tenant relationship, add matching `(workspace_id,id)` unique keys; for client rows add `(workspace_id,client_id,id)`. Composite FK mismatch must fail even if each UUID separately exists. FK `ON UPDATE RESTRICT` everywhere. Default `ON DELETE RESTRICT`; use `CASCADE` only for join rows and disposable, unfinalized draft children; use soft archive/status for clients, assets, accounts, categories and memberships. Never cascade-delete audit events, approval history, performance snapshots, finalized report versions, posted journals, finance snapshots or generated-document records. Implement row immutability through restricted privileges plus `SECURITY DEFINER` atomic transition functions with fixed `search_path`, and optionally defensive triggers. Table/column details must be rechecked against the chosen physical mapping before migration SQL is authored.
